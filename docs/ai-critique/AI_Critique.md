# AI Critique — HW06 API Testing

Student ID: `23127273`

During HW06, AI was strongest at producing large, well-structured test tables and Postman scaffolding, but weakest as an authority on how this particular SUT actually behaves. The most costly mistakes were not syntax errors; they were confident REST assumptions that never survived contact with `server.js`. For FR06, the model expected **404** for missing product ids and **401** on a public catalog read — both reasonable from generic API training, but wrong here: smoke tests showed **200 `{}`** and **200 with full JSON** respectively. For FR07 and FR16, AI listed input validation and admin role checks, yet still treated them as likely passes until execution proved the cart accepts `quantity=0` and a **user token can import products**.

The model failed for predictable reasons. Prompts showed the specification, not the implementation: no parity rule for even product ids, no in-memory cart merge logic, no missing `requireAdmin` middleware. AI also over-applied security templates (IDOR on public reads, auth on GET `/api/products/:id`) and under-applied code review — the gaps we added in the six extended cases per API. When Newman was wired with **spec-based `[SPEC]` assertions**, failures became evidence instead of prompts to "fix the test," which is the principle I will keep: AI may draft partitions and security ideas, but every expected status and schema must be validated against the spec **and** spot-checked against the SUT source; the human audit labels (VALID / INVALID / INCOMPLETE) are not paperwork — they are the gate before execution.
